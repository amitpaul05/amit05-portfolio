A company_admin account kept getting a 403 on our new documents API while the same token worked on every other endpoint. The account was fine and so were the migrations, because a superuser could upload without trouble. Every API we added before this one was a new endpoint on an existing model, so its group permissions were already in place. This time it was a whole new app, so migrate created fresh permission rows and nothing ever attached them to a group.

Curl settled it: documents came back 403 while manuals, answers and audits returned 200 on the same token. The real bug lived in our deploy script, which runs migrations on each release and nothing else, so the permission command had not run since someone last did it by hand. All four environments share that script, so I checked the blast radius before touching it, then added the command to the same gated deploy task. It runs once per release and fails the deploy loudly instead of crash-looping a live service.

The rest of the day went to the document linking API. One call now attaches a document to any number of requirements and manuals across audits, in a single transaction, with every target checked before the first write. A requirement with no answer gets one created as undeclared, so it stays open and keeps its slot in the score denominator instead of quietly improving someone's score.

Chasing that turned up an audit reporting 125% completion, where the query counted answers through their evidence files, so an answer with two files counted twice. I also closed a gap where a PATCH could attach another company's file to a manual. Ended on 272 tests green.

Neither bug was where the error message pointed. One was in a deploy script and the other was in a join.
