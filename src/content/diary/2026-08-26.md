A certificate download started failing with No wkhtmltopdf executable found, which looked like a missing package for about a minute. wkhtmltopdf is archived upstream, Debian 13 dropped it and Alpine never carried it, so there was no base image that could simply install it back.

I looked at four ways out: pin the image back to Debian 12, copy a static binary into Alpine, redraw the certificate in ReportLab, or move to WeasyPrint. I checked how the Govara backend does the same job before picking. WeasyPrint won because it was already in our requirements, the certificate stays as HTML so nobody has to rebuild it in code, and it removes an unmaintained binary instead of finding a new way to carry one.

That turned up a conflict already sitting in the lockfile. weasyprint 61.2 with pydyf 0.11.0 breaks on a changed constructor signature, so that pair had never worked at all. Pinned pydyf back to 0.10.0.

Two of our own bugs came out from under wkhtmltopdf as well. The certificate had been running to two pages with the signature falling onto the second, and static assets were being fetched over an absolute URL, so a gunicorn worker was issuing an HTTP request into its own worker pool. Neither was visible while the old renderer was doing the work.

Both build stages then moved to Alpine, uWSGI went back to the legacy VM and the entrypoint moved with it. A .dockerignore that leaves out the committed virtualenv and the stale upload buffers took the image from over 1.2GB to around 350MB, near 70% off. The log after the switch reads 200 application/pdf, one page, correct render, and webp assets still served under the right MIME type.

The error named a missing binary. The real problem was that the binary had been dead for a while, and while it lived it was hiding two bugs of ours.
